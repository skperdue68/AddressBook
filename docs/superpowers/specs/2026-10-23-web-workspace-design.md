# AddressBook member workspace and community insights

Date: 2026-10-23. Status: approved direction; user requested continuation on 2026-10-23. Prototype: outputs/AddressBook-web-design-preview.html outside this repository; throwaway sample data, not production code.

## Intent and agreed direction
Turn the existing bare administration portal into a useful, professional AddressBook workspace for ordinary members and authorized administrators. Members should register houses, manage collections, create/edit tours, and order tour stops easily from the web. Preserve Discord functionality and all existing access boundaries. Provide fun community statistics and evidence that people actively use AddressBook across Discord servers.

The user accepted the GuildSync-inspired dark navy interface proposal and existing-portal recommendation, with recent activity newest first, named usage across servers, and originating server names. Do not copy GuildSync assets. Reuse its general level of polish: application shell, clear typography, deliberate spacing, restrained accents, responsive panels and accessible controls.

## Goals, non-goals, anti-goals
Goals: member-friendly navigation; house search and registration; personal collection; tour creation/editing and drag/drop order; Featured and Random House discovery; meaningful statistics; global recent usage; administration grouped by task. Web and Discord share business rules.
Non-goals: replacing Discord, changing existing moderator authority, exposing Private records, full historical analytics reconstruction, live ESO visit tracking, a separate deployment or public anonymous data portal.
Failure conditions: admin privileges disclose Private records; web bypasses approvals; cross-environment writes; cached roles permit revoked access; tour drag/drop loses another editor's changes; statistical labels confuse copies with unique houses; telemetry contains private destinations or free-text searches.

## Approaches
1. Extend the existing Node HTTP portal (recommended and accepted direction). Reuse Discord OAuth, signed sessions, CSRF, database and services. Add member routes and a polished shared renderer with targeted browser JavaScript. Lowest deployment disruption; requires splitting member eligibility from existing blanket admin gate.
2. Separate frontend application and API. More frontend flexibility, but additional build/deployment complexity and duplicated integration work for the same initial features. Not selected.

## Workspace and visual structure
Header: selected Discord server and exact ESO environment, identity and sign out. Persistent desktop navigation and compact mobile navigation: overview, houses, housing tours, featured housing, statistics, My Address Book, authorized Administration, Help/access. An accessible Random House action is prominent on overview/discovery. Register House is a primary action.
Overview: shortcuts, personally relevant counts, featured content, recent global activity. Statistics: clearly scoped counts, official house popularity, distinct members/ESO owners, tour appearances and small fun facts. Tour editor: editable details, scope, stop cards showing destination/ESO owner, Add Houses, draggable order plus keyboard Up/Down, explicit Save and dirty-state feedback. Admin: Reviews & Reports; Access & Settings; Maintenance & Exports, with consistent Back navigation. Unauthorized tools are absent, and server authorization still checks every request.
Empty, pending, error and successful save states must be designed, not raw exception dumps. Mobile layouts stack panels, maintain readable tables or cards, and provide visible focus, labels and adequate contrast. Destructive changes use deliberate confirmation.

## Identity and authorization
Keep Discord sign-in. Signed-in members of bot-connected guilds can access member functionality for supported configured environments; administrative authorization is separate. Fresh Discord membership/settings are checked for each protected request; inaccessible or revoked contexts return a useful denial. Decouple member portal availability from whether the admin interface is configured as Discord or web. Preserve existing deployments with an explicit documented configuration migration/default.
Expand safe post-login internal redirects to the new routes without introducing external redirects. All writes use CSRF-protected POST requests and server validation; do not trust submitted creator IDs, scope permissions, guild IDs or env identifiers.
Extract/reuse a shared authoritative policy for Discord and web. Current generic AccessContextService.canEdit is not sufficient to encode administrator tour rights. Keep these rules:
- Private houses/tours: owner only, including against administrators and bot owners. Existing explicit share-pass capabilities remain narrow and do not permit editing or analytics disclosure.
- Server houses: creator or AddressBook Server moderator for that server, following the existing house rules.
- Global houses: creator or Global moderator in the same ESO environment.
- Server tours: creator, that server's AddressBook Server administrator, or Global administrator in the same ESO environment.
- Global tours: creator or Global administrator in that environment.
- Bot owners receive configured role capabilities, without overriding Private privacy.
- Editing a tour does not grant access to every stop. Scope/environment compatibility and visibility must be checked separately for playback, adding stops, sharing and exporting.
Never treat a native Discord administrator flag alone as AddressBook administrator authority. Preserve configured Server roles, individual grants, environment-specific Global grants and BOT_OWNER_IDS behavior.

## Your Access display
Show all applicable roles beside the signed-in profile: Bot Owner, Global Administrator with ESO environment, Server Administrator with server name, and Member when no elevated role applies. Explain effective capabilities briefly. Resolve from authoritative AddressBook configuration/grants/current membership, never Discord admin flags alone, and refresh when server/environment changes. Do not collapse multiple roles into one highest-role label or imply Private access.

## House and tour workflows
House registration reuses canonical catalog matching, existing duplicate handling, scope choices, approval/trusted registrant settings and active/pending statuses. Invalid/unmatched houses produce a helpful retry state. After successful registration, offer an eligible existing tour or create tour, consistent with pending/active eligibility. Editing uses the same restrictions as Discord.
House and tour browsing have pagination, useful filters, clear scope/owner labels, and alphabetical tour names. My Address Book provides the member's own records including Private.
Tour create/update/reorder is atomic. Keep a local editable draft and save explicitly. Recheck editor rights, every destination, environment/scope and duplicates within the transaction. Use an optimistic version or equivalent consistent snapshot token to reject stale saves with a reload/reapply message. Existing source records are not mutated by editing stop order. Multi-selection preserves the existing explicit order preview/reorder controls because browser/Discord selection order is not always reliable.

## Statistics semantics and boundaries
Counts are explicitly labeled: Your Private houses (requester only), Server registrations (selected guild), Global registrations (selected ESO environment), and accessible active tours. No total across other users' Private records, even for administrators.
Community popularity uses active accessible Server plus Global records in the selected environment. Group official house popularity by official house ID. Explain each selectable metric:
- Registrations: saved records, including legitimate distinct scoped registrations.
- Registered members: distinct registering Discord accounts for an official house.
- ESO owners: distinct normalized ESO owner identities within that environment for the official house.
- Tour appearances: distinct eligible visible tours containing the official house, not duplicated stops/copies.
Deduplicate cross-scope representations for unique destination/member/owner measures. Use canonical destination (environment, normalized ESO owner, official house ID). Distinguish official house types from individual furnished destinations.
Fun facts can include most represented official house, average active accessible tour length, and represented official house types. Do not claim visits, historical growth or completed tours from records that do not establish those events. Filters and drilldowns never widen access.

## Global recent activity and usage
Available to signed-in portal users across participating AddressBook servers; this global usage feed deliberately crosses the selected server boundary. Display newest first with a stable descending timestamp and ID cursor. Include member display name, human action, originating server name, source (Discord/web), relative time with exact accessible timestamp, and optional ESO environment. Provide server and action filters, pagination and an empty state. Never expose raw Discord IDs as presentation labels.
Capture successful meaningful actions: registrations, house/tour updates, tour creation/publication, actual tour starts, meaningful tour progress/completion when established, house searches, opening house/tour details, Random House, featured browsing, personal collection and ordinary web page use. Do not record every keystroke, pagination click, background poll or duplicate interaction delivery as a separate accomplishment. Emit one event per completed semantic action; a request/interaction ID provides retry deduplication. Denied/failed operations are not public usage successes. Security/admin audit remains separate; moderator decisions and approvals are not exposed as casual activity.
User requested named usage, including browsing, with server attribution. Public text for personal/Private actions is generic (e.g. Alex used My Address Book), with no target ID, destination, title, owner, search query, result count or private scope inference. Shared Server activity may show a generic action across servers, but record details and links are returned only after the viewer has current access. Global target links require matching eligible environment access. Deleted, newly Private, inaccessible or archived targets are rendered generically, not from a stale cached title. No content access can be inferred from an activity ID.
Web events use the selected active guild as origin; direct messages or contexts without a reliable guild say Personal session, never guess a server. Preserve a bounded display-name/server-name snapshot for attribution, escaped on rendering; server removal makes its history generic rather than revealing a formerly connected guild's details.
Implement a dedicated minimal usage event store, not a public projection of the security audit log. Store server-stamped UTC occurrence time, unique event ID, deduplication key, actor identity, origin guild/environment/source, allowlisted event kind, and only eligible nonprivate target reference. Never store tokens, free text, URLs with secrets or Private object identifiers in community telemetry. Generic private usage does not record a private-target reference.
Proposed builder defaults: 90-day raw event retention with scheduled bounded cleanup; totals labeled with the actual date range; counts reflect successful recorded actions and distinct active members, not ESO visits. Activity begins at deployment, with no fabricated backfill. Usage recording fails open for the original action, logs an operational error, and must not duplicate committed events on retries. Builder should select an outbox or post-commit idempotent mechanism appropriate to the existing transaction boundary.

## Bot-owner house catalog additions
Add an owner-only House Catalog tool in web Administration and Discord Administration. This manages official ESO house definitions, distinct from a member registering their furnished destination. Authorization must check the actor against configured BOT_OWNER_IDS on every form display and submission; Global administrators, Server administrators, approvers and Discord administrators cannot inherit this capability unless explicitly configured as bot owners. Do not repurpose a general moderator gate.
Owners can search existing catalog entries and add a new definition using the real positive in-game house ID, official name and zone, with optional supported classification/type/style, furnishing/collectible/population limits, acquisition/pricing details and verification/source metadata. Minimum requirements are the in-game ID and official name; unknown metadata remains null rather than fabricated. Discord may use a short initial modal followed by optional detail steps within component limits. Validate bounded text, nonnegative numeric metadata, safe source URLs and duplicate IDs; warn about possible normalized-name duplicates. Preview and explicitly confirm before insertion. No arbitrary ID allocation, overwriting an existing ID, bulk import, deletion or editing existing definitions in this scope.
Write to the deployed database catalog through a shared owner-authorized service, with CSRF for web, fresh actor validation in Discord, transactional insert, duplicate-race handling and an administrator audit entry. Catalog definitions are shared across ESO environments as the current model establishes; destination registrations remain environment-specific. Newly inserted houses become searchable in web and Discord without a code release or process restart; invalidate catalog caches if present. Never fetch a supplied URL server-side as part of this form.
Preserve owner-added definitions through startup, upgrades, backend transfer and backup. Existing seedHouses runs at startup and upserts packaged definitions by house ID; it must not silently overwrite an owner-added definition if a later bundled catalog includes that ID. Record ownership/provenance (additive metadata or companion table) and define collision behavior: retain owner-managed data, surface the mismatch for review, and never change destination foreign keys or house IDs. Tests cover owner-only direct requests, duplicate IDs including concurrent insertion, validation, immediate lookup, restart/seed collision preservation and backend transfer. Live Linux database operations remain deployment-only.

## Deployment database constraint
The user confirmed the authoritative database has moved to a Linux server. Do not use any old Windows development database as production data or migrate/copy it into the Linux deployment. Implement activity storage as a versioned additive schema migration for both supported backends, tested against disposable databases only. The deployed application already runs schema migrations at startup against its configured backend; Linux upgrade instructions must therefore require a verified database backup before starting the upgraded release, preserve the live DB_TYPE/DB_HOST/DB_NAME and related environment settings, and explain how to check the applied schema version and rollback/recovery limitations. A schema upgrade is distinct from the optional SQLite/MariaDB data-transfer MIGRATE feature; do not enable data transfer for this upgrade. No live Linux access or database mutation is authorized as part of local implementation. The activity table starts empty and collects new usage after deployment.

## Architecture, delivery and validation
Continue existing runtime and database conventions; avoid a new framework/build requirement unless justified during planning. Add scoped member services/routes, shared policy, small browser modules for the editor/filters, statistics queries and usage capture adapters used by Discord and web. New schema migration follows existing migration conventions. Preserve current admin URLs or redirect safely. No credentials or generated database/cache/build files in Git.
Suggested implementation order: shared policy/member entry; application shell; house workflow; tour editor; statistics; Discord/web usage instrumentation; grouped admin polish and documentation. Builder may refine task boundaries, CSS details, query indexes, event names and retention configuration without changing the agreed permissions/metrics.
Verify authorization matrix including revoked grants and cross-guild/environment IDs, owner-only Private records and exports, registration approval, stale concurrent tour saves, atomic stop compatibility, statistics deduplication, generic activity sanitization including later visibility changes, newest-first stable pagination, retry deduplication and telemetry failure behavior. Exercise keyboard/touch reorder, responsive screens, form feedback and login/CSRF flows. Run existing suite and relevant new tests, inspect rendered screens. Publish only through an isolated branch and PR after validation; do not edit installation or default branch.
